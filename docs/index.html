A review surface for machine memory

The Xylem Workbench

Twenty projects' worth of recorded decisions, constraints and gotchas — compiled, checked for rot, and reduced to the handful of judgement calls that actually need a person, delivered to a phone.

The two stores underneath are MCP servers, so the same memory is readable from Claude Code, Codex, a fresh Claude chat, the desktop app or the phone. A new session in any client opens with the project's decisions already in hand rather than blind, and a decision recorded in one client is in front of the next one, anywhere.

That is the difference from a wiki of files: a file has to be found and read. This is handed over at session start, and it ages honestly — which is what the rest of this page is about.

The problem

A memory that only grows is a memory nobody reads

Recording decisions is the easy half. The hard half is that a store ages: code moves under an entry, one decision quietly replaces another, a rule stops being retrievable because its tags were never sharpened.

None of that shows up as an error. Everything keeps working — the store answers every query, the tests stay green, and the rot is invisible until the moment you needed the rule that had silently stopped being served. The workbench exists to make that decay visible, and to put the decisions it produces somewhere they can actually be made.

Ask of any piece of work: is it arithmetic, or is it judgement? Arithmetic must never wait on a person. Judgement must never be automated.

That single line decides the whole design. The machine may compile, compare and propose; it may not decide. Get it wrong toward automation and a heuristic silently retires a rule that is still in force. Get it wrong toward caution and a hundred trivial repairs sit in a queue waiting for somebody to open a terminal. Both happened here, and both are below.

Architecture

Three repositories, one direction of flow

context-keeper holds the entries, cambium compiles them, and xylem-dashboard is the surface. Nothing in the browser ever touches a store: the phone reads a committed JSON file and writes back intents, and every write happens on the desktop, through the same lifecycle code a decision made in a terminal would use.

The three tiers

What is written, what is compiled, and what is judged

The distinction between these is the single most load-bearing idea in the system. Get it wrong and you either lose provenance or start letting a heuristic rewrite history.

TierAuthored byRegenerableWhat it is
EntriesA person, or an agent in sessionNo — source of truth Typed records: decision, constraint, pipeline. One store per project.
PagesThe compilerYes — fully, from entries A page records the exact entry ids it compiled from, when, and each source's status and content hash at that moment.
LawsJudgementNo Cross-project lessons. Promoted local → team → org; org-scope laws recall from every project and from a phone.

Staleness is computed, never guessed

A page is stale when any source entry was superseded, deprecated, or changed since the page compiled. The comparison is on (status, updated_at, content_hash) — with the hash authoritative, because the stores are hand-editable and a backfill can move a timestamp on text that never changed. The page names the entry that caused it.

Why the hash wins. Trusting updated_at alone means a maintenance script that rewrites every record's timestamp marks every page stale overnight, and a hand-edit that fixes a typo in place marks none. Both readings are wrong in the direction that costs you trust in the signal.

A law's equivalent: unincorporated evidence

For laws there is no compiler to diff against, so the check is different: find every entry carrying two or more of the law's topic tags that the law does not cite. What's left is the work list. Two-tag overlap is a hint — measured precision on that class of signal is about 22% — which is exactly why each one surfaces as a proposal somebody rules on, never as an automatic edit.

The surface

Six views, each answering one question

It is scanned, not read. Summary before detail; state encoded in shape as well as number, so what needs attention reads at a glance on a phone held one-handed.

The remaining two views are quieter. Projects is entry counts by kind and status. Chains draws supersession edges as a graph — including dangling ones, because a store reaches that state on its own when a target is pruned, and drawing it honestly beats hiding it.

A drain on the desktop picks it up

Every five minutes: read the queue, act, clear it. It holds a lockfile, because the scheduler has no concurrent-run protection and two overlapping drains would back up a store the first had already rewritten — destroying the very snapshot that made the first one recoverable.

Everything affected is copied before the first write, so a run that dies halfway restores to where it started rather than a midpoint nobody chose.

Delegation

“Send for eval” — and the mistake inside it

Judgement, then, and the hard half of it. Some proposals cannot be settled from a summary on a phone, so that button files a self-contained request carrying both entries in full — the reading needs nothing but the file.

The agent is the session. There is no runner, and there must never be one.

The first implementation shelled out to a billed headless model call, fired from the five-minute timer — a metered charge per request, unattended, shipped switched on. That is a standing cost dressed as a feature. It was deleted rather than disabled, because a flag that can be flipped is not a guarantee.

The second attempt was to wire a local model instead. Same mistake in different clothes: everything the request contains is already in the reading agent's context. The correct design is that a request simply waits, and a hook surfaces it the moment any session opens — so the noticing is automated while nothing is ever spawned.

Both directions were got wrong here. A hundred and nine trivial repairs once sat in a queue for twenty minutes because nobody happened to open a terminal, which is what moved the mechanical half into the drain.

One repair that must never be automated

A drifted entry — one whose code has moved underneath it — can be “fixed” by writing anything to it at all, because updating stamps a fresh verification timestamp and drift is measured from that stamp. The flag clears without anyone reading the code.

So thirty-seven repairs were deliberately left undone. Doing them automatically, at machine speed, across twenty projects would have been the worst available version of that bug: a mesh that reports itself verified everywhere and has checked nothing.

A safeguard that can be satisfied by touching the thing it guards is not a safeguard.

What repair looks like from the far side

Applying those hundred and nine links changed a hundred and nine entries — and two hundred and one compiled pages immediately went stale, because their sources' content hashes moved. Nothing broke; the pages simply stopped claiming to be current.

That is the staleness model doing the one thing it exists for. A repair in one tier propagated to another without anybody tracking the dependency by hand, and the rebuild that answers it is arithmetic, so it needs one tap and no reading at all.

Security

Four gates, because one is a single point of failure

The snapshot carries every project's memory, including private repositories and local-only work. This is the part that was got wrong first, and the reason it is now checked on every deploy.

01 Path-token authentication

The site is served only beneath a secret path segment. No token, no bytes.

02 Worker runs before assets

A platform setting, and without it the gate does not exist — static assets are served before the Worker by default. The first deploy served the entire snapshot to the open internet for four minutes because of exactly this.

03 Allowlist build

The publishable bundle is assembled by naming files, never by excluding them. Nothing travels because nothing happened to exclude it.

04 Verified on every publish

The deploy script fetches the snapshot, the script and the index without the token and throws if any of them returns success. A deploy that silently loses gate 02 must fail loudly, not quietly go public.

The rule that came out of it. Never deploy data before the gate has been proven on a data-free build. The tooling to do that already existed and was skipped, which is the whole lesson: a safeguard you built and then did not use is not a safeguard.

Standing rules

Invariants

Each of these is a bug that already happened, written down so it happens once.

  • Never spend money. No metered call, no billed CLI, never on a timer, and never offered as an option without its price attached — an option chosen without its cost is not informed consent.
  • Never write to a store from the browser or the Worker. Intents only.
  • Pages are artifacts; laws are judgement. Recompile freely. Never auto-write a supersession or a citation from a heuristic.
  • Bump the asset version everywhere at once. Sweep every occurrence rather than hand-picking — a missed entry in the precache list caches URLs the page never requests, so it holds nothing useful and offline serves an empty shell. Invisible online.
  • Never bulk-edit an entry flagged as drifted in order to fix something else on it. Updating stamps a fresh verification timestamp, which clears the drift flag without anyone re-reading the code — silencing the warning by touching it.
  • Status colours are reserved. A recommendation uses the accent, never a status colour, and never colour alone.

Field notes

Failures worth keeping

These cost real time and none of them announced themselves.

A span ignores height

Meters, bars and status dots need to be block-level. Computed style will happily report the right colour while nothing paints — the same trap landed three separate times in one file before it was written down.

A single em-dash killed an unattended job

Redirected output on Windows defaults to a legacy codepage, and one dash raises an encoding error that takes the whole run down. It costs nothing interactively, because a console that renders it never complains.

The shipped binary was four months behind its own fix

A scheduler's Python jobs hung forever and recorded nothing — including a daily medication reminder that had therefore never fired. The repository had been correct the whole time; only the artifact was stale. That failure looks like nothing at all from a dashboard, which is why the diagnosis started from a probe rather than from the logs.

A filtered view answered a question it was not asked

A directory listing with a name filter hid a folder, which led to a confident and wrong conclusion about how the application was packaged. Twice in one session a diagnosis came from one observation where a second would have contradicted it.
